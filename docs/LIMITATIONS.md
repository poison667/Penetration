# Known Limitations — Meridian Platform

Explicit, honest limitations. Nothing here is a hidden simplification: each entry says
what is NOT implemented, why, and what the platform does instead. Requirement rows in
REQUIREMENTS_COVERAGE_MATRIX.csv cross-reference these IDs.

| ID | Limitation | Status & detail |
|----|-----------|-----------------|
| **L-1** | **Automated scanning finds a subset of all issues.** | By nature. The platform reports *measured* findings with evidence and confidence, separates FACT from INFERENCE, and never claims exhaustive coverage. Methodology sections in every report state this. |
| **L-2** | **Linux installers are now built and verified locally; Windows installers and GUI launch-testing are not.** | All three Linux installers (`.deb`, `.rpm`, `.AppImage`) were really built in this workspace from the one shared codebase (`npx @tauri-apps/cli@2 build --bundles deb,rpm,appimage`, exit 0) using a user-space WebKitGTK 2.52.6 sysroot, and structurally verified (metadata, contents, ELF, 143 in-image dependency resolutions, embedded SPA assets — §3b10, artifacts + SHA-256 + recipe in `/home/user/installers/`). What remains genuinely unverified here: (a) the **Windows** installers (.exe NSIS / .msi WiX) are produced by the committed CI workflow (green runs 7896316/d1920b0; both installers are attached to the v1.0.0 GitHub release alongside the Linux ones) — this sandbox has no Windows runner or wine, so no local .exe/.msi exists (a local `cargo-xwin` cross-compile was attempted and is resource-blocked: rustc OOM-killed on the `windows` crate at `-j1` under the sandbox's 2 GB RAM — §3b10; the recorded recipe works on any ≥4 GB machine); (b) the sandbox is **headless** — no display, so the GUI binary was never launched; install/run testing on a real Linux desktop (and Windows 10/11) is still open; (c) the AppImage leaves `libasound.so.2` external by linuxdeploy's upstream system-lib exclusion policy (ubiquitous on desktops; deb/rpm pull it transitively). `npm run verify:desktop` (30 checks, in the gate) still verifies every build input. See D4/C3. |
| **L-3** | **OCR requires an engine at runtime; scanned-PDF rasterization is not implemented.** | Image OCR is fully real when the optional `tesseract.js` dependency is installed (WASM Tesseract, offline language data vendored in `vendor/tessdata/`) or a system `tesseract` binary exists — probed at runtime, executed in a crash-contained worker thread, absence reported honestly otherwise. PDFs without a text layer still need page rasterization (rendering PDF pages to bitmaps), which no zero-dependency runtime provides — such documents report their status rather than fabricating text. |
| **L-4** | **Browser-level rendering checks (real Chrome CWV / DOM screenshots) are out of runtime scope.** | No browser engine is embedded. Performance checks measure real server-side signals (TTFB, body bytes, caching, compression, asset weight budgets) and clearly label client-side CWV as inference. DOM/visual monitoring uses content hashing + keyword presence, not pixel diffing. |
| **L-5** | **SMS notification delivery is not implemented (webhooks and email are).** | Webhook delivery is fully real: registered endpoints receive HMAC-SHA256-signed POSTs (`x-meridian-signature`) with retry/backoff (3 attempts, 15/60/300s), observable in the deliveries log. Email delivery is a real SMTP client (EHLO/MAIL/RCPT/DATA) against your configured relay. SMS requires an external carrier contract/credentials, which no development environment can provide — it is deliberately not stubbed or faked. |
| **L-6** | **PDF writer is minimal by design (zero-dependency).** | PDF 1.4 with core Type1 fonts, headings, paragraphs, severity tables, pagination, and embedded sha256. No image embedding or custom fonts. HTML/XLSX/CSV/JSON reports carry the full fidelity. |
| **L-7** | **AI analysis quality is bounded by the local provider.** | The default provider is a deterministic, evidence-grounded retriever-summarizer (BM25 + citation), not an LLM. It cannot fabricate (answers cite evidence and carry a grounded flag), but it is not as fluent as a hosted model. External providers plug in via configuration. |
| **L-8** | **Data workbench operates on file-based datasets (CSV/XLSX/JSON), not federated databases.** | Upload → profile/cleanse/dedupe/transform/anomaly → download is fully implemented. Live database connectors are not part of this build. |
| **L-9** | **Single-process deployment.** | API + worker share one process in `--mode=all` (or can be split). Horizontal scale-out (multiple workers on one store) is designed-for (lease-based queue) but not exercised at scale here. |
| **L-10** | **Some security checks are profile-gated.** | Active/intrusive checks (raw-socket verb tampering, HTTP smuggling, overflow probes) only run in `standard`/`full` profiles against explicitly authorized assets, rate-limited, with destructive payloads blocked. Passive coverage still runs everywhere. This is a deliberate safety constraint, not a gap (D7). |

- **Manual-work hub (v1.1.0):** manual findings are recorded as entered — the
  tester, not an engine, is the measurement instrument (check kind
  `assisted`); the platform enforces the evidence invariant (a tester note
  and/or attached exchanges) but cannot independently verify a human's claim.
  HAR import covers the standard HTTP Archive 1.2 format (browser DevTools,
  Burp Suite, OWASP ZAP exports); proprietary Burp project XML and ZAP session
  files are not parsed. Imported exchanges are evidence, not scans — they do
  not create findings by themselves and are never counted as measurements.
